TextBox 4: What simulated annealing is 
TextBox 8: 1 · Search

TextBox 11: Better moves are always kept. Worse moves can still be kept early on, by chance.
TextBox 12: 3 · Cool down

TextBox 15: Why it helps
TextBox 16: Think of the search like walking over hills. Today’s method only walks uphill. That is fast and safe, but you can get stuck on a steep part of the hill when a better peak is nearby.

Simulated annealing sometimes takes a downhill step early, so you can leave a trap and reach a better overall schedule. As the search “cools,” those downhill steps become rare, and we settle on the best plan we found.
NOTES: So what is simulated annealing.

Simulated annealing is a search method. The idea comes from metalworking: heating metal allows it to bend, then cool it slowly so it settles into a strong structure. In optimisation, “heat” means we are more willing to try unusual moves. “Cooling” means we become stricter over time.

There are three simple steps.

First, search. We propose a change to the maintenance schedule — for example, shift a check a few days earlier or later — then evaluate the new plan with the same availability score we already use: minimum availability first, then smoothness, then average. We are not inventing a new scoring system here.

Second, accept. If the new plan is better, we keep it. That part is familiar. The difference is early in the search we may also keep a slightly worse plan, by chance. That sounds odd, but it is deliberate. A temporary worse move can get us out of a local minima.

Third, cool down. As the search continues, we accept fewer and fewer worse moves. Near the end, we mostly behave like today’s method: keep improvements, reject clear steps backwards.

So if we were walking up a hill, sometimes we might need to take a step downhill just to find a better path rather than constantly going up a hill that might be steep. If we accept worse moves temporarily, we might find an easier path.

What annealing does need later is a fair acceptance rule for those temporary worse moves — because our score is a ranked tuple, not one number. That is an acceptance detail, not a new objective. Next I will show how this idea maps onto the  | optimiser |  we already built.

NOTES: So how does annealing fit our design?

We will keep how we still focus on the worst availability days first. We still rebuild an aircraft’s schedule after a move, so the A, B, C, D rules stay valid. We still update availability cheaply instead of recalculating everything. We still try larger timing shifts, then smaller ones. And we still remember the best schedule we have seen so far.

On the change side: currently we only keep improving moves. That is classic hill-climbing. The new method is annealing acceptance — better moves always; worse moves sometimes, more early, less later. We also drop the improve-only early-exit so worse candidates can actually be tried.

So the fit is clean if we think in layers. Annealing does not replace how we find candidate moves. It replaces how we decide whether to accept them. Keep the smart search. Change the acceptance rule.

TextBox 3: FAIR ACCEPTANCE
TextBox 4: Fair testing
TextBox 27: 1 · Better plan?
TextBox 28: If the new schedule improves worst-day availability, keep it. That always comes first.
TextBox 29: 2 · Worse worst-day?
TextBox 30: If it lowers the minimum availability, reject it. Do not accept a “smoother” plan that makes the busiest day worse.
TextBox 31: 3 · Same floor?
TextBox 32: If the worst day is unchanged, but the plan is bumpier or lower on average, allow it sometimes early, less often as the search cools.
TextBox 33: What we report, and how we test
TextBox 34: Because annealing is random, run the full search 3 times and report the typical result. Current priority selection NS method needs one run, do not compare the best of three with one baseline run.
NOTES: This slide covers two things: how we treat a worse move, and how we know which plan to keep.

Checklist. If the new schedule improves the worst day, keep it. If it makes the worst day worse, reject it. If the worst day stays the same but the plan is bumpier, annealing may accept that sometimes early, less often later.

We keep two plans. Current can go downhill so we can keep searching from it. Best-so-far only updates when something beats it — that is what we report.

Because annealing is random, we run the full search three to five times. We report the typical result, not the lucky best. Today’s method is deterministic, so one run is enough. Do not compare best-of-five annealing with one baseline run.

NOTES: Third workstream: settings.

Several choices are already baked into today’s search: how far we move a check, how long we let it run, and whether we stop at the first improvement. If we add annealing, we also choose how quickly we become stricter.

Those choices affect both schedule quality and runtime, but we have not tested which ones actually matter.

So we will change one setting at a time on the heavy forecast, and watch worst-day availability and runtime together. The output should be a short list of settings that move the needle — not endless tuning. Document the result, then decide.

NOTES: Fourth: the starting schedule.

Our method starts from the loaded plan and only makes local changes. A well-staggered start can make the final result look better than the algorithm alone deserves. A bunched start can make a good method look weak. A “win” might just be a luckier start.

Priority-based selection does not make that start irrelevant. It only chooses which events to try first — those sitting on the worst availability days. If a worst-day event has an improving move, other events are not even considered that iteration. So non-bottleneck stagger is mostly inherited from the loaded plan. That is a reason to test controlled starts, not a reason to skip them.

So we will build a few controlled starting plans — bunched, as-loaded, and more spread out — and run the same search from each.

Today’s method and annealing get those same starts. We only call annealing better if it wins from the same starting plans. That keeps the comparison honest.

NOTES: What we will keep, and when we stop.

Keep annealing if the worst-day availability is at least as good as today, and it is not much slower. New operational rules still have to produce legal, usable schedules. And the gain has to come from the method — not a luckier start or a luckier random seed.

If annealing does not beat today’s method, we keep today’s method. If worse moves start hurting the worst day, we tighten the acceptance rule. If new constraints break feasibility, we do not ship them.

We only keep what the evidence supports.

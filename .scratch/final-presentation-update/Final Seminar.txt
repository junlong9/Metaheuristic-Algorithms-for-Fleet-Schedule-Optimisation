SLIDE 2
Title 1: The scheduling problem
Content Placeholder 2: Concurrent maintenance creates dips in fleet availability.
Retiming checks must preserve start windows and maintenance rules.
First: maximise worst-day availability.
Then: reduce standard deviation.
Finally: improve mean availability.
NOTES: The scheduling problem starts when several aircraft enter maintenance at similar times. Availability then falls even if the average across the year looks acceptable. The decision variable is the start of a check inside its legal start window. Checks must not overlap on one aircraft, and changing one check must preserve the sequence and the reset rules for later checks. The score ranks worst-day availability first, lower population standard deviation second, and mean availability last. A smoother schedule cannot compensate for a lower worst day. Random failures and resource shortages motivate the problem, but the reported experiments model scheduled maintenance. Source: CONTEXT.md and the completed technical report dated 12 October 2026. | 2

SLIDE 6
Title 1: Scaling the search
Rectangle 1: The heavy fleet creates over 1,000 neighbours per iteration.
Full evaluation becomes too slow.
Sampling 200 neighbours reduces work.
Random selection can miss a useful move.
Priority selection targets checks that cause the worst days.
NOTES: When the same neighbourhood search scaled to the heavy forecast, an iteration could produce over a thousand candidate schedules. Fully copying, checking, and scoring each one was expensive. Sampling two hundred neighbours reduced the work but introduced uncertainty, because the sample could omit a useful improving move. The next change used the structure of the problem: checks covering the worst availability days are the most relevant place to search first. Priority selection therefore concentrates the work deterministically, while widening the search when a worse priority group cannot improve. Source: Iteration 1 milestone slides 5 to 7. | 6

SLIDE 7
TextBox 3: MILESTONE 4 · PRIORITY-BASED SELECTION
TextBox 4: Priority selection searches the worst availability regions first
TextBox 6: Rank events by the worst availability during their interval.
Search the worst priority level first, expand only if needed.
Move one check, then rebuild later events using A/B/C/D rules.
Update incrementally by removing old intervals and add the rebuilt intervals and score once.
Deterministic, rule-compliant, and substantially faster.
Measured result: min 15→18, std 1.96→1.44.
NOTES: This is the method I want to spend the most time on, because it is the main technical result of iteration 1.

Priority-based selection changes the question we ask. Instead of asking “what happens if we try random moves to find the best one?”, we ask “which maintenance events are actually hurting and causing the minimum availability to be the lowest?”

How this algorithm works is for every event, it gets a priority score equal to the lowest fleet availability of the event for every day it is active. So if an event overlaps a day when only fifteen aircraft are available on that day, then the event priority score is fifteen. Then the events with the lowest priority score will be the ones to be shifted first.

Another thing I changed is that when we move one check, we do not leave the rest of that aircraft’s plan sitting in a potentially broken state. Before,  | when we move one maintenance check, only that selected event is shifted. Now when an event is shifted, the schedule is rebuilt, everything earlier on the same aircraft stays exactly as it was. Everything later is recalculated from the new shift date using the A/B/C/D rules, so the due dates will remain legal even after getting shifted. | 

I also changed how scoring works. The entire fleet is not deep copied for every trial. We rebuild one aircraft, then update availability incrementally. That aircraft’s old intervals are removed from the stored availability array, and the new rebuilt intervals are added, and scored once. That is much cheaper than recomputing availability from scratch for every  | neighbour | .

NOTES: Each check receives a priority equal to the lowest fleet availability during its maintenance interval. A check covering a day with fifteen available aircraft has priority fifteen. Checks then belong to exclusive priority groups. In this illustration, twenty checks touch the worst days, so a pair of timing shifts produces around forty proposals at that first group. The baseline chooses the best improving move within the first group that can improve the score. If none improves, it expands to the next group. After a move, the later checks on that aircraft are rebuilt and availability is updated incrementally. This combines targeted selection with lower evaluation cost. TextBox 12: Classic single-chain simulated annealing remains an earlier ablation
NOTES: The baseline is an improving priority hill-climb. The candidate is basin-hopping with tabu polish, built on the same maintenance neighbourhoods. It first obtains a polished schedule, perturbs it to leave the current local optimum, and uses tabu search to polish the new schedule. Temperature then determines whether to continue from a worse basin. The best-so-far schedule is tracked separately and is the result we return. This is more structured than simply accepting every generated neighbour along one annealing chain. Classic simulated annealing remains an earlier ablation and is not the candidate in the comparison that follows.
